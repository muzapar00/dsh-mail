日志的边界

给 dsh-mailbox 加一层落盘日志时，我们怎么决定「记什么、怎么降级、承认什么做不到」。
设计与实现：费加罗；审阅与挑漏：图恒宇。

插件最难受的不是报错，是没有现场：热重载失败、工具忽然不见、收信时断时续——这些时刻往往只留下一个空白的终端。我们要的是一层便宜的、能翻的日志，让「刚才发生了什么」有据可查。

三条硬约束

  • 不能成为新的故障点。日志写失败，收发信照旧。
  • 不能记下不该记的东西。正文、附件名与内容、授权码，一概不落。
  • 不能压垮主链路。调用方从不等待写入，队列有界，宁可少记一行。

做法

  • 降级链。文件写不了，就把状态交给宿主日志喊一声：[dsh-mailbox] event log degraded (not a failure): lost N line(s) …。宿主也没有，才算真丢——这句写在代码与 README 两处，防的是半年后的人以为这层兜底万全。
  • 字段白名单。只落 ts / level / event / detail 与少量 data；ts 一律 UTC ISO8601（带 Z）。
  • 卸载路径。短 flush 之后若仍有未记的丢弃，补一行 log-recovered（带 dropped 与 since）；仍不可写，降级到宿主日志。
  • 轮转与封顶。按日切、保留 14 天、单文件 2 MiB 封顶；启动时把当日文件已有字节数种进计数（同日重载也不会越界），跨日时再清一次旧文件。
  • 防风暴。同一 event + 归一化 detail 在 60 秒内只落首行，末了补一条汇总（count / since / until）：「发生了多少次」比「每条都留着」有用。
  • 脱敏。detail 落盘前把邮箱地址、绝对路径、长串 ID 换成 <email> / <path> / <id>：仍看得出「发生了什么、发往哪类对象」，看不出是谁。

承认做不到的

不保证一条不丢

进程若在宿主 logger flush 之前被硬杀，最后一行仍可能丢。要一条不丢，得在数据目录留 dirty 标记、启动时对账——那是另一层复杂度，当前不做。

保留期到了就清

旧文件被清理是设计行为，不是故障；日志只作近期参照，不作长期存档。

丢弃计数只活在内存里

droppedSince 不随文件传递，跨重启的恢复行只报重启之后那一段，不是全程数。

汇总行与恢复行不参与封顶

极端情况下以「有界溢出」顶过单文件上限，属设计取舍，不做额外裁剪。

怎么验

四步现场，加上两步边界：启动行与 config 行；同步行；热重载的 dispose 紧跟 ready（时间差本身是判据）；断写权限后补写恢复；卸载时仍只读则宿主日志降级上报；跨重启看有无 dispose，判断上次是否干净退出。

另有单测与双平台 CI（ubuntu / windows），以及仓库里 docs/verification/ 下的现场日志样例。

{"ts":"2026-11-12T11:22:06.420Z","level":"info","event":"dispose"}
{"ts":"2026-11-12T11:22:06.672Z","level":"info","event":"ready","detail":"version=0.2.0"}
{"ts":"2026-11-12T11:23:06.580Z","level":"info","event":"log-recovered","data":{"dropped":1}}

日志是给「此刻」用的。它证明的是「记下来了」，以及——更重要的——「记不下来也不出事」。
